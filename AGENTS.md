# Working on Prospector II

- Keep the main-branch root README strictly for players. Put build instructions, source layout and internal development notes in `docs/development.md` or other developer guides, not the player introduction.

- Read `docs/design-philosophy.md` before gameplay/balance work. Preserve the intended harsh roguelike: frequent early deaths, lethal bad luck, progress that buys breathing room, and difficulty escalating with run age independently of player progress. Do not treat a player or test pilot death alone as a defect. The full escalation curve is design direction, not a claim of current implementation.

- Edit `src/`, then run `npm run build`. `index.html` is generated and remains the single-file release artifact. Never patch it directly.
- Maintain the current release version only in root `package.json`. The build injects runtime/HTML labels and synchronizes desktop metadata; `npm run check` rejects stale versions. Do not manually bump generated copies or rewrite historical version references. See `docs/architecture.md`.
- **Backward save compatibility is not a requirement.** Do not add migrations, compatibility shims or work to preserve obsolete save formats unless the user explicitly requests it. Change/bump the career schema when useful and clearly reject unsupported saves. Keep current-format validation, transactional save integrity and preservation of the active career on load failure.
- Start with `docs/architecture.md` and `docs/source-map.md`; search relevant functions and callers instead of reading the entire game. Skip `src/assets/sprites.js` unless editing embedded images.
- `src/build-manifest.json` is the explicit assembly order. Preserve the order and script boundaries. These files share globals; they are not independent ES modules.
- Preserve localStorage keys, inline-handler function names, DOM IDs, turn progression, startup order, and 1400 x 720 root layout unless the task explicitly changes them.
- Check callers as well as definitions. New biomes affect generation, creatures, tile/ASCII rendering and scans; crew statuses affect ticking, combat, UI and saves; dialogue changes affect state, available options and barter.
- Reserve the full-width message banner for specific critical conditions that require immediate action. Send routine events, NPC speech, and radio traffic to the sidebar log.
- Support keyboard and mouse play through the same game actions. The compass handles pointer movement, wait, and cursor placement. Map clicks select tiles in Examine, firing, and landing-scan modes. A second click on the mouse-aimed tile confirms a shot. Use explicit controls for movement, pickups, and landing confirmation. Keep essential information available through keyboard selection or examination. Hover is a preview.
- Keep the shortcut legend collapsed by default. Its key labels use muted, static text. Place the toggle beside the legend.
- Run `npm test` after building. For runtime changes, open the built HTML in a browser and check the affected behavior. Syntax/build checks alone do not establish gameplay correctness.
- `npm run verify:migration` audits the initial extraction against the recorded original HTML hash. It is deliberately separate from normal tests because later gameplay edits should change that hash.
- `src/html/legacy-design-notes.html` is an unchanged historical comment embedded in the release for exact migration parity. Some descriptions and line references are outdated; current code and `docs/architecture.md` take precedence.
- Do not edit or package Windows executables as part of source organization work.
- Prefer deterministic scenario tests against actual game functions and scripted headless integration checks. Do not navigate the game through browser-control tools unless the user asks. Automated checks cover rules and persistence; report separately what still needs human playtesting.
- Keep reusable playthrough controllers and headless scenario scripts versioned under `qa/`, with portable paths, dependency setup and documented limits; see `qa/README.md`. Run the relevant scenarios when their behavior changes. Keep generated traces, screenshots, checkpoints and personal saves out of commits. The user needs automation available on a fresh computer, not personal-career transfers.
- `experiment/expedition-legacy` is the active experimental branch; `main` is the public release. The old development tips are preserved as archive tags (see `docs/branch-history.md`).
- Autosave persistence is asynchronous and transactional; see `docs/autosave.md`. Await confirmed save/load results for transitions and tests. Keep current/previous record commits atomic, current-format validation sound, stale-window writes guarded, failure/export UI visible and debug worlds excluded. The legacy localStorage key is no longer the latest-save authority.
- Keep `CHANGELOG.md` current in the same commit as every meaningful gameplay, balance, UI, debugging, architecture or development-workflow change. Include date/version/branch, implemented behavior and reason, validation actually performed and its limits, save impact, removals/reversals and unresolved work. Update affected current guides and roadmap status; do not describe planned features as implemented. Documentation-only work needs no game-version bump. Read the latest entries when resuming development and link the relevant entry at handoff.
- Keep the debug playground complete. Register every new galaxy object/scenario in `DEBUG_GALAXY_OBJ_TYPES` with an interactive factory. Terrain, biomes, store/debug items, commodities, implants and creature body catalogs are read dynamically by `src/debug/playground.js`; add new content to its owning runtime catalog rather than a separate gallery list. Add scenario adapters for context-dependent NPCs/buildings. Run the palette coverage checks and verify the new sample's real interaction, reset and return-to-career behavior. Never let sandbox autosaves, exports or test analytics replace career state.
